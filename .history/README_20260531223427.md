# Internshala Internship Search — Clone

A frontend clone of Internshala's internship search page built as a learning project. The goal was to replicate the real search and filter experience as closely as possible — live data from Internshala's API, client-side filtering, fuzzy search, and a component structure that mirrors how production React apps are built.

**Live site:** https://internshala-red.vercel.app/internships

---

## Setup

You'll need Node.js 18+ on your machine.

```bash
git clone https://github.com/your-username/internshala-clone.git
cd internshala-clone
npm install
npm run dev
```

Open [http://localhost:3000](http://localhost:3000) — it redirects to `/internships` automatically.

```bash
# Production build
npm run build
npm start
```

### Shadcn/ui setup (first time only)

This project uses shadcn/ui components. If you're setting it up from scratch:

```bash
npx shadcn@latest init
npx shadcn@latest add checkbox slider input badge skeleton separator button popover calendar
```

## How Data Fetching Works

Data fetching is handled by a single TanStack Query hook — `useInternships`. It calls Internshala's `/hiring/search` endpoint, maps the raw response to a typed `Internship[]` array, and caches the result.

```
Page loads → useInternships fetches once → data cached for 5 minutes
User changes a filter → no API call → useMemo re-runs filterUtils on cached data
```

The hook is called exactly once in the whole app — inside `InternshipsPageClient`. The `staleTime` is set to 5 minutes, meaning if you navigate away and come back within that window, no refetch happens.

TanStack Query also handles loading and error states out of the box — no manual `useState` for `isLoading` or `isError`.

## How Filtering Works

All filtering is client-side. The core of it is a pure function in `lib/filterUtils.ts`:

```ts
filterInternships(internships: Internship[], filters: FilterState): Internship[]
```

It takes the full cached data and current filter state, runs each active filter in sequence, and returns the matching subset. This runs inside a `useMemo` in `InternshipListSection` — it only recomputes when `data` or `filters` change.

After filtering, results are sorted by `postedAt` descending (newest first) before rendering.

### Filters available

| Filter | Type | How it works |
|---|---|---|
| Profile | Text + fuzzy | Fuse.js match on `title` field |
| Location | Text + fuzzy | Fuse.js match on `location[]` field |
| Work from home | Checkbox | `isWorkFromHome === true` |
| Part-time | Checkbox | `isPartTime === true` |
| Min stipend | Slider | `stipend.min >= selectedValue` (0 = no filter) |
| Starting from | Date picker | `startDate >= selectedDate` |
| Max duration | Pill selector | `durationMonths <= selectedValue` |
| Job offer | Checkbox | `hasJobOffer === true` |
| Fast response | Checkbox | `isFastResponse === true` |
| Date Posted | Pill selector | `postedAt >= now - cutoff` (see below) |
| For women | Checkbox | `isForWomen === true` |

## Fuzzy Search — Why Fuse.js

The profile and location inputs don't do a simple string match. They use Fuse.js, which does token-aware fuzzy matching. So searching "developer" surfaces "Full Stack Developer", "Python Developer", "Frontend Developer" — not just exact matches. This is how the real Internshala filter panel behaves.

Two separate Fuse instances, tuned differently:

- **Profile** — `threshold: 0.35` — looser, so related job titles show up
- **Location** — `threshold: 0.2` — stricter, so "Mumbai" doesn't accidentally match "Pune"

Both instances are memoized with `useMemo` and only recreated when the suggestions list changes — never inside a render cycle.

Autocomplete suggestions are built from the fetched data itself — unique titles for profile, unique city names for location. No Google Maps API, no extra network calls.

## Date Posted Filter — Why I Added This

The real Internshala shows an "Early Applicant" badge on some listings, but it's vague — it depends on their internal logic and you can't control it as a filter.

I replaced it with a **Date Posted** filter that gives you actual control over how recent the listings are:

| Option | What it shows |
|---|---|
| Any time | Everything — no filter applied |
| Today | Posted in the last 24 hours |
| Last 3 days | Posted in the last 3 days |
| Last 7 days | Posted in the last 7 days |
| Last 30 days | Posted in the last 30 days |

It uses the `postedAt` field from the API response. The sort order stays the same regardless — newest first always. Only the visible subset changes.

This felt like a more honest and useful filter — you know exactly what you're filtering by.
